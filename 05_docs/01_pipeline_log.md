# Pipeline log: from raw reads to gene-ID crosswalk

This is a narrative record of how the RNA-seq preprocessing pipeline
(`../02_preprocessing/`) was run on the HPC cluster, complementing the
executable scripts there. The scripts are the canonical, runnable versions;
this document explains the reasoning and the order of operations behind
them.

## 1. Raw data transfer

Raw paired-end FASTQ files (57 samples, Novogene sequencing delivery) were
transferred from local storage to the HPC cluster's working directory
(`$PROJECT_ROOT/Bulk_RNA/raw_data/`).

## 2. Building the sample sheet

nf-core/rnaseq requires a CSV sample sheet listing each sample and the
absolute paths to its paired FASTQ files. This was generated by scanning the
raw-data directory for per-sample subfolders and writing out
`sample,fastq_1,fastq_2,strandedness` rows (all libraries were unstranded).
See `02_preprocessing/02_nfcore_rnaseq/making_samplesheet.sh` for the exact
script, and `02_preprocessing/02_nfcore_rnaseq/samplesheet.csv` for the
resulting table.

## 3. Reference genome preparation

Three genome builds were used throughout the project (see
`02_preprocessing/01_genome_download/Downloading_Medfly_Genomes.sh`):

- **Short-read / well-annotated reference**: NCBI RefSeq `GCF_000347755.3`
  (Ccap_2.1)
- **Long-read reference**: GenBank `GCA_905071925.1` (EGII-3.2.1)
- **Deschepper et al. 2024 assembly**: downloaded from Zenodo record
  `13928607`

Some annotation files needed light repair before use:

- The short-read GFF3 was converted to GTF with `gffread`, then passed
  through an `awk` fix-up because a subset of features were missing an
  explicit `gene_id` attribute (STAR/featureCounts require one). The fix
  falls back to `gene_name`, `gene`, `transcript_id`, or `protein_id`, in
  that order, whichever is present.
- The Deschepper assembly's GFF used a different scaffold-naming convention
  (`Scaffold_*`) than its own FASTA headers; scaffold names in the GFF were
  rewritten to match (`Scaffold_*` → `ScaffoldCc_*`) before the annotation
  could be used.

## 4. Running nf-core/rnaseq

The RNA-seq quantification pipeline (`nf-core/rnaseq` v3.23.0, run via
Apptainer/Singularity under SLURM) was launched three times — once per
genome build — using per-build Nextflow configs
(`02_preprocessing/02_nfcore_rnaseq/configs/rnaseq_slurm_*.config`) and launch
scripts (`02_preprocessing/02_nfcore_rnaseq/nf_core_*_RNA_seq.sh`). Each run:

1. Loads the required environment modules (`nextflow`, `apptainer`, a Python
   distribution).
2. Builds/refreshes the sample sheet.
3. Sets Nextflow/Apptainer cache and work directories under the project
   root.
4. Runs `nextflow run nf-core/rnaseq` with `-profile apptainer`, the
   per-build config, the sample sheet, and the genome FASTA/GTF (or GFF for
   the Deschepper build).

Each run writes STAR/Salmon alignment and quantification output, including
the merged gene-level count and TPM matrices under
`star_salmon/salmon.merged.gene_{counts,tpm}.tsv`. The small merged matrices
for the short-read and long-read builds are included in this repository
under `02_preprocessing/05_results_summary/`. Per-sample BAM files are not
included (large and regenerable), and the Deschepper-build count matrices
are pending a re-run of that pipeline branch — both are available on
request from the repository maintainer in the meantime.

## 5. Building the cross-genome gene-ID crosswalk

Because the three genome builds were assembled and annotated independently,
their gene IDs and scaffold coordinates don't correspond directly — a gene
studied in the short-read annotation needs to be matched to its counterpart
in the long-read and Deschepper annotations before results from different
builds can be compared. This crosswalk was built via reciprocal-best-hit
(RBH) protein search:

1. **Decompress** each genome's FASTA and GFF3.
2. **Parse GFF3 → transcript-to-gene table** with a small Python helper
   that walks `gene` and transcript-type features (`mRNA`, `transcript`,
   `lnc_RNA`, etc.) and records gene ID, gene name, and biotype for each
   transcript.
3. **Extract protein sequences** with `gffread`, then **keep only the
   longest isoform per gene** (a second Python helper), since RBH search
   is done at the gene level, not the transcript level. Protein FASTA
   headers are rewritten to the gene ID so DIAMOND hit IDs map directly
   back to genes.
4. **Run DIAMOND blastp in both directions** (A vs B, B vs A) between each
   pair of assemblies, at high sensitivity.
5. **Identify reciprocal best hits**: for each protein, keep only its single
   best hit in the other assembly by bit score, then keep only pairs where
   each side is the other's best hit. Results are filtered by minimum
   percent identity, query/subject coverage, and E-value (defaults: ≥50%
   identity, ≥50% coverage on both sides, E-value ≤ 1e-10).

This was run for three assembly pairs — short-vs-long, short-vs-Deschepper,
long-vs-Deschepper — producing three pairwise RBH tables, which were then
joined into a single three-way `medfly_master_gene_map.tsv` crosswalk
(short-read ID ↔ long-read ID ↔ Deschepper ID). See
`02_preprocessing/03_gene_id_crosswalk_rbh/` for the runnable `.slurm` scripts
and the resulting small TSV tables.

## 6. GO annotation

Two independent GO annotation sources were prepared for downstream
enrichment analysis (see `02_preprocessing/04_go_annotation/`):

- **eggNOG-mapper** (primary source used in the R analysis): run against
  both the short-read and long-read proteomes.
- **InterProScan**: run as an alternative/cross-check annotation source,
  with a Python helper converting InterProScan's TSV output into a
  2-column `gene_id \t GO_id` table.

The resulting gene-to-GO mapping tables were compacted into
`geneID2GO_short.rds` / `geneID2GO_long.rds` for direct use with `topGO` in
the R analysis.
